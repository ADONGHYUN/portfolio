01

주문·재고·적립금 / 초과 예약과 역순 잠금

재고 예약·만료 처리의 동시성

MariaDB · 초과 예약 방지, 신규 주문·만료 배치 경합과 롤백 검증

문제
동시 예약의 초과 판매와, 신규 주문·만료 배치가 재고·적립금을 반대 순서로 기다리는 교착 위험
선택
조건부 UPDATE로 예약하고, 회원 선잠금·READ_COMMITTED·상태 재검증으로 만료 처리 보호
검증
마지막 재고는 1건만 예약. 주문 준비·만료 배치 경합, 중복 반환과 실패 후 롤백 확인
재고 예약·만료 배치의 설계와 검증

원인과 제약

조회와 갱신이 분리되면 조회 시점의 수량을 갱신 시점에 보장할 수 없습니다. 주문의 예약 경쟁과, 관리자 상품 편집이 최신 재고를 덮어쓰는 충돌은 보호할 범위도 달랐습니다.

대안과 선택 이유

모든 요청에 같은 락을 걸지 않았습니다. 예약은 가용 수량 조건이 포함된 원자적 UPDATE로, 물리 재고 차감과 이력 기록은 비관적 락으로, 관리자 수정은 expectedVersion을 비교하는 낙관적 충돌 검사로 나눴습니다. 예약은 별도 조회 없이 수량 조건과 갱신을 묶고, 차감은 변경 전후 수량과 이력을 함께 보호하기 위해서입니다.

실제 구현

가용 재고 = 실물 − 예약 − 판매 보류입니다. 조건을 만족한 행 수가 요청한 옵션 수와 다르면 트랜잭션 전체를 롤백합니다. 여러 옵션은 ID를 정렬해 처리하고, 옵션 마스터와 inventory_option_balance의 version을 분리했습니다.

요청옵션·수량 정규화
→
DB 조건가용 재고 ≥ 요청량
→
예약조건부 UPDATE
→
결과변경 행 수 검사
→
트랜잭션전체 커밋 / 롤백

검증 시나리오와 결과

MariaDB 통합 · 통과재고 1개에 동일 옵션 예약 요청 2건을 동시에 실행
두 스레드를 같은 시작 신호로 출발시키고 서비스의 독립 트랜잭션에서 각각 1개를 예약했습니다. 1건 성공·1건 재고 부족 거절, 최종 reserved_quantity = 1로 초과 예약이 없었습니다. 격리된 로컬 MariaDB 11.4 · 2026.09.20.
H2 통합 · 통과재고 5개·1개인 두 옵션에 각각 2개 예약
한 옵션의 재고가 부족하면 전체 예약이 롤백되어, 두 옵션 모두 예약 수량 0개를 유지했습니다.
H2 통합 · 통과주문 조회 뒤 상품이 판매 중지·숨김 상태로 변경
갱신 시점의 판매 조건으로 예약을 거절하고, 함께 요청한 다른 옵션의 예약도 롤백했습니다.

운영 보호 장치예약 가능한 수량을 DB의 갱신 조건으로 강제합니다. 여러 옵션을 함께 예약할 때 하나라도 조건을 충족하지 못하면 전체 예약을 롤백해, 일부 상품만 예약된 상태가 남지 않도록 처리합니다.

신규 주문과 만료 배치가 서로를 기다리던 경로

주문 준비는 재고를 잡은 뒤 적립금을 예약하고, 만료 배치는 적립금을 반환한 뒤 재고를 풀었습니다. 두 트랜잭션이 상대가 가진 잠금을 기다릴 수 있어, 배치가 주문을 잠그기 전에 대상 회원 전체를 회원 ID 순서로 먼저 잠그도록 맞췄습니다.

회원 잠금만으로는 다른 회원의 INSERT를 막는 부재 적립금 사용 내역의 gap lock을 해결하지 못했습니다. 만료 배치를 READ_COMMITTED로 실행하고, 주문 잠금 후 상태·만료 시각을 다시 검사합니다. 최종 취소의 조건과 변경 행 수도 확인합니다.

MariaDB 통합 · 2026.10.28

주문 준비와 다회원 만료 배치 경합
재고 예약 직후 두 흐름을 교차 실행해 모두 완료되고 재고·적립금이 일치함을 확인했습니다. 적립금 미사용 주문의 정리와 다른 회원의 신규 적립금 예약 경합도 확인했습니다.
같은 주문을 두 배치가 동시에 처리
주문 취소·재고 반환·적립금 반환 원장이 한 번만 반영됐습니다.
예약·반환 뒤 실패를 주입하고 재시도
최종 주문 쓰기 실패 시 반환 전체가 롤백되고 재시도는 한 번만 반영됐습니다. 적립금 부족으로 주문 준비가 거절돼도 재시도에 주문·예약·원장이 남지 않았습니다.

범위와 처리 비용기본 20건씩 처리하고 재고는 옵션별로 합산해 반환합니다. 적립금은 원장·유효기간 규칙을 보존하는 기존 서비스를 재사용해 주문 수에 비례하는 비용을 유지합니다. 회원 잠금 대기와 다른 경로의 교착 가능성은 남으며, 전체 시스템의 교착 제거를 의미하지 않습니다.

핵심 구현: 재고 예약 SQL

가용 수량과 판매 상태를 UPDATE 조건에 함께 둔 실제 예약 SQL입니다. 변경된 행이 1개가 아니면 서비스에서 예외를 발생시켜 예약을 확정하지 않습니다.

UPDATE inventory_option_balance
  SET reserved_quantity = reserved_quantity + #{quantity},
      version = version + 1
  WHERE option_id = #{optionId}
    AND stock_quantity - reserved_quantity - sales_hold_quantity >= #{quantity}
    AND EXISTS (
        SELECT 1
        FROM product_option po
        JOIN product p ON p.product_id = po.product_id
        WHERE po.option_id = inventory_option_balance.option_id
          AND po.deleted_at IS NULL
          AND po.option_status = 'SELLABLE'
          AND p.deleted_at IS NULL
          AND p.product_status = 'ACTIVE'
    )
02

PortOne·KakaoPay / 중복·지연·순서 역전을 테스트로 재현

중복 결제 처리 방지

H2·PG 모의 검증 · 원장·알림·재고 이력 각 1건

문제
승인 알림을 다시 처리하거나 늦은 승인으로 만료 주문을 되살릴 위험
선택
PG 재조회 후 주문·결제 상태를 잠금 안에서 확인하고 한 번만 반영
검증
H2·PG 모의 서버: 중복 승인에도 원장·알림·재고 이력 각 1건

관리자 화면에서 확인하는 주문·환불 상태

백엔드의 상태 구분을 관리자가 판단할 수 있도록 화면에도 연결했습니다.

결제 처리 설계·검증 과정

원인과 제약

결제창, webhook, PG의 실제 상태는 같은 시점에 갱신되지 않습니다. 알림 도착 순서를 결제 상태로 믿을 수 없어 중복 승인, 과거 실패 이벤트, 주문 만료와 늦은 승인을 나눠 다뤘습니다.

대안과 선택 이유

클라이언트 성공 응답이나 webhook의 이벤트 이름만으로 주문을 완료하지 않습니다. 서명 검증 후 PG를 재조회하고, 서버에 저장한 결제 시도와 대조합니다. PG 조회는 DB 상태 변경 트랜잭션 밖에 두어 네트워크 대기 중 잠금을 유지하지 않습니다.

실제 구현

주문 준비 때 가격·배송비를 서버에서 계산하고 재고를 예약합니다. 회원의 결제 확정은 회원 행을 먼저 잠그고 주문 → 결제 시도 순으로 잠근 뒤 paymentId·주문·상점·통화·금액과 PAID 상태를 확인합니다. 이미 처리한 원장이 있으면 재고를 다시 차감하지 않고 반환합니다. 새 결제의 원장·주문 완료·재고 차감·알림 outbox는 같은 트랜잭션에 기록합니다.

주문 준비가격 계산·재고 예약
→
결제 요청결제 시도 저장·PG
→
알림 / 재조회서명 검증·PG 조회
→
DB 검증회원 → 주문 → 결제 시도
→
커밋원장·주문·재고·알림

검증 시나리오와 결과

H2 + PG 모의 서버 · 통과동일 PAID webhook 동시 처리
결제 원장·알림 outbox·재고 차감 이력이 각각 1건만 생성.
H2 + PG 모의 서버 · 통과승인 이후 과거 FAILED/CANCELLED 이벤트 도착
PG의 최신 PAID 상태 유지. 중복 완료·환불·재고 변동 없음.
H2 + PG 모의 서버 · 통과PG 조회 지연 중 주문 정리 배치가 먼저 만료 처리
주문을 다시 완료하지 않고 늦은 결제 복구 건을 1개 생성. 보상 취소 후 재실행은 추가 처리 없음.
단위 테스트 · 통과주문 준비의 결제 ID 불일치·취소 전 금액 불일치
잘못된 결제 완료·취소를 거절하고 재고를 변경하지 않음.

운영 보호 장치만료 후 승인된 결제는 이미 반환한 재고를 다시 차감하지 않고 환불 복구 대상으로 분리합니다. 자동 취소를 확정할 수 없는 경우는 수동 검토로 남겨, 불확실한 결제를 정상 주문으로 처리하지 않습니다.

03

이미지 공개 처리 / 부분 성공과 작업 재시작을 테스트로 재현

S3와 DB의 부분 실패 복구

H2·S3 모의 검증 · 복사 요청 2회, 객체 생성 1회

문제
S3에는 파일이 생겼지만 DB에는 완료 기록이 없어 재시도 판단이 불확실
선택
DB에 outbox를 남기고 외부 복사와 완료 기록을 분리
검증
H2·S3 모의 객체: 중단 후 복사 요청 2회에도 객체 생성은 1회
이미지 복구 설계·검증 과정

원인과 제약

DB와 S3는 하나의 로컬 트랜잭션으로 커밋할 수 없습니다. 복사 응답 유실이나 실행기 종료를 단순 실패로 취급하면, 이미 만들어진 파일을 모른 채 같은 작업을 다시 실행할 수 있습니다.

대안과 선택 이유

외부 I/O를 긴 DB 트랜잭션에 넣는 대신 작업을 DB outbox에 남겼습니다. 별도 메시지 브로커 없이 기존 DB에서 재시도 상태를 관리하되, DB 기록과 파일 저장 사이에 일시적인 상태 차이가 생기는 방식임을 전제로 했습니다.

실제 구현

이미지 자산과 COPY 작업을 같은 트랜잭션에 저장합니다. worker는 짧은 트랜잭션으로 작업을 선점한 뒤 트랜잭션 밖에서 복사합니다. 응답이 불확실하면 HEAD와 메타데이터를 확인하고, 유효한 lease 소유자만 완료 상태를 기록합니다.

DB 트랜잭션자산 + COPY outbox
→
작업 선점lease 발급·커밋
→
외부 I/OS3 COPY / HEAD
→
결과 검증키·크기·해시 확인
→

원인과 제약

여러 요청이 동시에 갱신하면 앞선 요청이 교체한 토큰을 뒤의 요청이 다시 제시합니다. 반대로 교체된 토큰을 계속 허용하면 탈취된 토큰의 사용을 끊기 어려워, 교체 직후의 짧은 경합을 별도로 처리했습니다.

대안과 선택 이유

JWT Access Token은 프론트 메모리, Refresh Token은 HttpOnly Cookie로 분리해 장기 토큰을 스크립트가 직접 읽지 못하게 했습니다. 서버는 원문 대신 SHA-256 해시와 세션 계열(family)을 저장합니다. 매 갱신마다 교체하되 정상 동시 갱신 충돌과 오래된 토큰 재사용을 다르게 처리합니다.

실제 구현

사용자 행 잠금과 조건부 revoke로 이전 토큰을 한 번만 교체합니다. ROTATED 후 5초 이내 요청은 동시 갱신 충돌로 거절하되 새 토큰을 발급하거나 family를 폐기하지 않습니다. 그 이후 재사용은 해당 family를 폐기합니다.

→

→
유효 토큰조건부 revoke
→

→
응답Access + 새 Cookie

운영 프로필의 Refresh Cookie 기본값은 Secure·SameSite=Strict입니다. 관리자 API는 서버에서 ADMIN/OWNER, AI 개발 기능은 OWNER 권한을 검사하며 화면 숨김에만 의존하지 않습니다.

AI 활용과 검증

개발 요청은 로컬 PC의 격리된 소스에서 실행하고, 모델의 완료 응답과 실제 명령·테스트 결과를 분리합니다. 소유자 승인 뒤에도 기준 파일 해시가 달라지면 원본 반영을 중단합니다.

상품 상세 제작은 입력 스냅샷·불변 revision·상품 기준 해시로 생성 기준과 반영 대상을 구분합니다. 생성 중 상품이 바뀐 결과를 그대로 덮어쓰지 않도록 했습니다.

AI/Codex는 분석·구현·테스트·리뷰를 보조했습니다. 업무 규칙과 변경의 채택·검증·배포 책임은 제가 맡습니다.

개발 요청 실행·승인 구조

웹은 요청·상태·결과를 저장하고, 개발 PC 실행기가 분석 → 계획 → 구현 → 실제 명령 검증 → 독립 리뷰를 진행합니다. 운영 서버에서 빌드나 테스트를 실행하지 않습니다.

JSON Schema로 단계 결과를 제한하고, heartbeat·lease로 실행기의 작업 소유권을 관리합니다. 원본 반영은 승인과 기준 파일 검사를 거치며 commit·push·운영 배포는 자동 실행하지 않습니다.

아키텍처와 데이터 모델

상품 수정이 과거 주문을 바꾸지 않도록 스냅샷을 남기고, 주문 만료와 늦은 결제 승인을 별도로 관측합니다. 앞의 문제 해결 사례를 뒷받침하는 시스템 구성과 핵심 데이터 관계입니다.

현재 규모의 선택주문·결제·재고의 핵심 변경은 하나의 DB 트랜잭션에서 다룹니다. 서비스 간 분산 트랜잭션 없이 핵심 데이터의 정합성을 유지하고, DB와 외부 시스템 사이의 실패는 outbox·재조회·보상 처리로 복구하도록 구성했습니다.
