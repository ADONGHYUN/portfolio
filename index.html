개발 도구 · 1인 개발 과정의 자동화

AI 개발 작업 오케스트레이션

웹에서 받은 개발 요청을 코드 변경, 실제 검증, 소유자 검토와 원본 반영까지 연결했습니다.

고운맘 개발에 AI를 폭넓게 활용하면서 요청 분석·구현·검증·리뷰를 단계로 분리했습니다. 운영 서버는 작업과 결과를 관리하고, 개발 PC의 로컬 실행기가 코드 수정과 테스트·빌드를 수행합니다. 무거운 개발 작업을 커머스 운영 서버에서 실행하지 않는 구조입니다.

Verifier는 모델 응답이 아닌 실행기의 실제 명령 실행 단계입니다. 백엔드 테스트와 프론트엔드 lint·build, 계획에 지정한 추가 검증의 종료 결과를 리뷰에 전달합니다. 실패하거나 실행하지 않은 필수 검증은 승인 대기로 넘기지 않습니다.

원본을 보존하는 격리 수정

백엔드·프론트엔드의 미커밋 변경까지 복사해 기준선으로 보존합니다. 각 모델 역할은 독립 세션에서 JSON 제안을 반환하고, 실행기가 경로·크기·계획을 검사해 허용된 파일에 적용합니다.

응답 유실에 대비한 재전송

DB 행 잠금으로 작업을 순차 선점하고, heartbeat·lease·fencing token으로 이전 실행기의 늦은 응답을 차단합니다. 결과는 로컬 journal에 먼저 저장해 응답 유실 시 같은 결과만 재전송합니다.

검토·승인과 원본 반영 분리

웹에서 전체 diff와 변경 전후를 검토합니다. 승인 후 별도로 원본 반영을 요청하면, 승인된 변경 버전과 대상 파일 전체의 기준 해시를 확인한 뒤 백업과 반영을 진행합니다.

실패 상황을 다루는 검증 시나리오

서버 응답 유실
저장된 결과만 재전송하고 완료한 모델 단계를 다시 실행하지 않도록 구성했습니다.
원본 파일 충돌
대상 중 한 파일이라도 기준선과 다르면 원본 쓰기를 시작하기 전에 중단합니다.
반영 도중 사용자 편집
사용자가 다시 편집한 파일은 보존하고 실행기가 변경한 파일만 복구합니다.
화면 검토
격리 코드의 PC·모바일 화면을 비교하며, 캡처만 필요한 요청은 모델 호출과 코드 수정 없이 처리합니다.

구현 코드와 자동 테스트 시나리오를 기준으로 정리했습니다. 생성 결과 검토·승인과 원본 반영은 별도 단계이며, 커밋·푸시·운영 배포는 자동 실행하지 않습니다. 이 구조의 생산성 향상률은 아직 측정하지 않았습니다.

DESIGN RULES

한 테이블의 상태만 보고 완료로 판단하지 않습니다.

  • 주문 스냅샷상품명·가격·배송정보의 당시 값을 보존
  • 상태 분리주문·결제·환불·배송 상태를 독립적으로 관리
  • 동시성 경계옵션 마스터와 실시간 재고의 version을 분리
  • 운영 이력재고·배송·수동 판정과 알림 재시도를 추적

커머스 데이터에 더해 AI 개발 작업은 단계·검증·승인 이력으로, 상품 상세 제작은 입력 스냅샷·이미지 자산·불변 revision으로 관리합니다. 아래 ERD에서 회원 참조는 비회원·탈퇴 주문을 위해 선택값이며, 옵션·재고의 1:1은 도메인 생성 규칙을 포함합니다.

외부 알림은 주문 트랜잭션과 분리합니다. 일시 실패는 재시도하고, 발송 결과가 불확실하면 별도로 보류해 중복 발송 위험을 관리합니다.

01 · Snapshot

과거 주문을 현재 상품 정보로 다시 계산하지 않습니다.

상품명·옵션·단가·배송지·배송비 정책은 주문과 주문상품에 당시 값으로 보존합니다.

02 · Consistency

옵션 마스터와 실시간 재고의 충돌 경계를 분리했습니다.

상품 편집은 master version, 주문·결제·재고 조정은 inventory version만 변경해 서로의 작업을 방해하지 않습니다.

03 · Operations

실패와 수동 판단도 데이터로 남깁니다.

결제·환불 수동 검토, 배송 변경, 알림 재시도와 이미지 outbox를 운영 이력으로 추적합니다.

공개 포트폴리오에는 핵심 관계와 대표 컬럼만 표시했습니다. 정확한 제약조건·인덱스·전체 테이블은 docs/schema.sql을 기준으로 관리하며 실제 회원·주문 데이터는 포함하지 않습니다.

문제 해결

데이터 흐름으로 설명하는 문제 해결

결제·재고·AI 상품 제작을 대표 사례로 골랐습니다. 데이터 흐름과 문제·해결·결과를 함께 정리했습니다.

01

결제 상태 수렴

SDK 성공보다 서버에 남은 주문·결제 상태를 최종 기준으로 사용합니다.

문제

결제창 응답과 webhook은 순서가 다르고 같은 이벤트가 다시 올 수 있습니다. 화면, 주문, 결제 원장이 서로 다른 결론을 내리면 출고와 환불도 잘못됩니다.

해결

webhook 검증 후 결제사 API를 다시 조회하고 저장된 식별자와 대조했습니다. 주문과 결제 시도를 정해진 순서로 잠그고, 늦은 승인은 자동 환불 또는 수동 검토로 분리했습니다.

결과

중복 완료, 지연 승인, 결제 상세 불일치와 webhook·reconciliation 경합을 테스트했습니다. 프론트도 서버 주문 상태가 확정된 뒤 완료 화면을 표시합니다.

02

원자적 UPDATE, 낙관적 락, 비관적 락을 쓰기 경로의 성격에 맞게 조합합니다.

문제

옵션 정보와 재고가 하나의 version을 공유하면 고객 주문이 관리자 상품 편집까지 충돌시킵니다. 사전 조회만으로 재고를 판단하면 동시 주문에서 초과 예약이 발생하고, 중복 결제 webhook은 재고를 두 번 차감할 수 있습니다.

해결

옵션 마스터와 실시간 재고의 테이블·version을 분리했습니다. 주문 예약은 가용 수량 조건을 포함한 원자적 bulk UPDATE, 관리자 수정은 version CAS, 결제 확정은 주문·결제 시도와 optionId 오름차순 재고 행을 FOR UPDATE로 잠근 뒤 movement까지 한 트랜잭션으로 처리했습니다.

결과

실제 MariaDB 동시 실행에서 재고 1개를 요청한 두 주문 중 한 건만 성공했고, 동일 PAID 요청이 겹쳐도 결제 원장·재고 차감·movement가 한 번만 반영됐습니다. 고객 주문 뒤에도 상품 설명과 이미지는 재고를 덮어쓰지 않고 저장됩니다.

문제

여러 이미지를 생성하다 일부만 실패하거나 응답이 끊기면 같은 컷을 다시 생성할 수 있습니다. 제작 중 상품이 바뀌면 예전 결과가 최신 상세를 덮어쓸 위험도 있습니다.

해결

컷별 상태·결과를 저장하고 입력 스냅샷과 불변 revision을 분리했습니다. 생성 결과가 불확실하면 자동 재생성을 멈추며, 이미지별 검토와 상품 기준 해시 확인 후 상세·이미지만 반영합니다.

성공한 컷을 보존한 재시도, 특정 컷·문구 수정, 이전 결과 복원을 구현했습니다. 생성 재시도와 상품 반영 재시도를 분리해 업로드·활성화 실패만 재처리할 수 있습니다.

기능·계약과 테스트 시나리오 기준입니다. 실제 생성 품질과 운영 배포 여부, 작업 시간 절감 효과는 별도로 확인해야 합니다.

04

MariaDB 기반 Public API Rate Limiter

공개 API의 요청 횟수를 IP와 사용자 식별자 범위로 나눠 관리합니다.

Public API로그인 · 주문
→
1차 gateIP bucket
→
식별자HMAC-SHA256
→
MariaDB행 잠금 · count
→
응답허용 · 429 · 503

문제

IP만 제한하면 분산 공격에 약하고 식별자만 제한하면 공격자가 임의 값으로 버킷을 계속 만들 수 있습니다. 메모리 방식은 재시작과 다중 인스턴스에서 횟수가 초기화됩니다.

해결

IP를 먼저 검사하고 통과한 요청만 IP+식별자와 식별자 버킷을 확인합니다. 원문은 HMAC으로 보호하고, MariaDB 행 잠금과 독립 트랜잭션으로 동시 요청과 rollback에서도 횟수를 유지합니다.

결과

정확한 허용 횟수, Retry-After, 시간 창 초기화, 동시 요청, DB 장애와 제한된 배치 삭제를 검증했습니다. DB 부하나 hot-row 대기가 커지면 Redis로 옮길 기준도 정했습니다.

S3 이미지 처리의 재시도와 복구

DB와 외부 저장소를 한 트랜잭션으로 묶을 수 없는 문제를 상태로 추적합니다.

→

문제

S3 작업은 DB commit과 함께 rollback할 수 없습니다. 응답 유실이나 worker 중단이 발생하면 파일은 존재하지만 DB 상태는 실패로 남을 수 있습니다.

해결

DB에는 자산과 outbox 상태를 먼저 남기고 외부 I/O는 트랜잭션 밖에서 수행합니다. worker는 lease로 구분하고 timeout 뒤에는 S3 HEAD로 실제 결과를 다시 확인합니다.

결과

commit·rollback, 응답 유실, worker 재시작, 동시 lease와 활성화 순서 역전을 테스트했습니다. 삭제 전에는 보관 기간과 현재 상품 참조를 다시 확인합니다.
